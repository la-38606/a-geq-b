How A≥B works

A≥B proves a polynomial inequality by finding an explicit algebraic certificate and re-verifying it with exact rational arithmetic. The search may be heuristic or numerical; the acceptance never is. This page walks through the pipeline, the trust boundary, and the code that implements them.

The pipeline

Every proof follows the same five steps. Here they are on the smallest interesting example:

  1. Parse
    a2 + b2 ≥ 2·a·b: the claim becomes a syntax tree. Assumptions after given become hypotheses.
  2. ↓
  3. Normalize
    a2 − 2·a·b + b2 ≥ 0: the claim reduces to a single polynomial target p = A − B ≥ 0, with denominators cleared.
  4. ↓
  5. Search search
    The prover looks for a way to write p as a sum of squares with nonnegative rational weights: a Gram matrix over a monomial basis, factored exactly by rational LDLᵀ. Constrained claims get Positivstellensatz strategies; hard targets get a numerical semidefinite solver (below). Search is allowed to fail.
  6. ↓
  7. Candidate
    (a − b)2: an explicit claimed identity, nothing more. It carries no authority yet, whatever search produced it.
  8. ↓
  9. Exact check trusted
    The checker expands the certificate with exact rational arithmetic and compares normal forms: does 1·(a − b)2 equal the target, term for term, with every weight ≥ 0? No floats, no tolerance, no “close enough”.
  10. ↓
  11. PROVED
    Only an accepted certificate licenses this word. Everything shown on the prover page (the identity, the LaTeX, the Lean theorem) is read off the verified certificate.

The trust boundary

The design is the classic certificate (LCF-style) architecture: an untrusted search side that may do anything, and a small trusted core whose acceptance is the only path to proved.

Untrusted search
  • exact Gram search over candidate monomial bases
  • constrained strategies: constant multipliers, reduction modulo equalities, products of hypotheses
  • numerical SDP in Python (cvxpy) with floating point
may fail, may be wrong; the worst case is a missed proof
candidates cross the boundary; trust does not
Trusted core
  • canonical polynomial arithmetic over exact rationals (zarith)
  • the certificate checker: expand, compare normal forms, check signs
small enough to audit; its soundness is proved in Lean

“Untrusted” does not mean malicious; it means allowed to be wrong. A bug anywhere on the search side (a bad heuristic, a numerical solver gone astray, even a wrong reconstruction) produces a candidate the checker rejects, and the run honestly reports that no certificate was found. A bug can lose a proof; it cannot invent one.

When exact search is not enough

Finding a sum-of-squares decomposition is, in general, a semidefinite feasibility problem: the Gram matrix has free entries, and some choice of them must be positive semidefinite. The exact search resolves only a little of that freedom (a bounded grid over at most two free entries). For the rest, A≥B uses a numerical solver, without letting a float anywhere near the verdict:

OCaml emits the Gram SDP
a-geq-b sdp-emit → cvxpy finds an approximate
PSD matrix (floats) → OCaml rounds to exact rationals
and reads off squares (LDLᵀ) → exact check

The rounding tries a ladder of denominators; each attempt either yields a certificate the checker accepts or is discarded. If none survives, the answer is no certificate found, never “probably true”.

What the statuses mean

PROVED
A certificate passed the exact checker. The identity on screen is the proof; you can re-verify it independently.
NO CERTIFICATE FOUND
The searches came up empty. Not a disproof: the claim may be false, may be true but not a sum of squares (Motzkin’s polynomial), or may need a certificate beyond the implemented searches. A≥B never concludes “false”.
INVALID INPUT
The claim did not parse or reduce (e.g. division by a non-constant polynomial).
CERTIFICATE REJECTED
A proposed or imported certificate failed exact verification. The boundary held.

The Lean layer

Two separate things are machine-checked in Lean 4 / Mathlib, and it is worth being precise about which is which:

  • The checking rule itself is verified. lean/AeqbCheck.lean re-expresses the checker over MvPolynomial (Fin n) ℚ and proves, axiom-clean and without sorry: if checkSOS p cert = true then p evaluates nonnegatively at every real point. The trusted core is not merely small and audited; its acceptance criterion is a theorem.
  • Each proof can be exported as its own Lean theorem. a-geq-b lean (or the button on the prover page) emits a self-contained file: the sum-of-squares identity is closed by ring, nonnegativity by positivity. Lean’s kernel checks it when you compile the file; A≥B itself does not run Lean, and the interface never claims it did.

Three languages, three jobs

OCaml
Everything that must be exact: the algebra, the parser and normalizer, the certificate formats, the trusted checker, and the search orchestration. Dependencies: zarith (exact ℚ) and yojson.
Python
Untrusted numerics only: cvxpy solves the Gram semidefinite program and hands back an approximate matrix. It could return garbage without endangering soundness.
Lean
The formal layer: the checker-soundness theorem, and one exportable kernel-checkable theorem per proof.
View the code structure

The OCaml library is layered so that each module depends only on those above it; the trusted core is the top of the list, and nothing in it depends on any search code.

The canonical form

x2y → [2,1]   x2 → [2]   1 → [ ]

Monomials are exponent vectors with trailing zeros stripped, so x2 has one representation no matter how many variables are in scope, and polynomials map canonical monomials to nonzero coefficients only. Every operation preserves this normal form, which is what lets the checker decide the certificate identity by structural equality; the entire soundness argument rests on that comparison being exact.
